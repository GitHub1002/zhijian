# 代码评审与分支管理

## 分支

- `main` 只接受已经通过评审的变更。不在 `main` 上直接提交功能。
- 功能分支从最新的 `main` 拉出，名称使用 `feat/`、`fix/` 或 `docs/` 加简短说明。
- 一个分支只做一件事。制度文案修改不和检索逻辑改在同一分支，除非不一起发布就会互相矛盾。

## 评审要求

- 至少 1 名熟悉该模块的同事批准后才能合并。作者不能批准自己的请求。
- 评审看正确性、权限是否在服务端校验、失败时用户能否理解下一步，以及是否把密钥或本地数据带进仓库。
- 评论要指出文件和具体问题。只写“再看看”的，作者可以要求补充。
- 有权限、认证、数据删除的改动，描述里写明如何验证拒绝路径，而不只写成功路径。

## 合并前

1. 与 `main` 同步，解决冲突。
2. 语法检查和已有测试通过。
3. 变更说明写明用户可见行为，没有可见变化时写“无界面变化”。
4. 确认 `.env`、数据库文件、向量索引和个人截图不在提交列表中。

## 常见问题

**问：紧急修复能否先合并再补评审？**
生产止血可以先回滚到已发布版本，不把未评审分支直接推到生产。新的修复仍须有人批准；批准人当时不在时，由值班负责人先审风险，下一工作日补正式评审。
