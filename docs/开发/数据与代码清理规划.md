# 数据与代码清理规划

> 目标：在不破坏现有问答、权限、反馈和评测功能的前提下，清理旧版兼容代码、
> 未使用表和冗余列，让代码和数据库只保留当前实现需要的部分。

## 1. 背景

项目从 1–5 星评分、个人记忆和旧版前端一路演进到现在的：

- 👍/👎 反馈
- 检索轨迹
- 规则分诊
- 内容任务
- 精选正例
- 在线实验
- RAGAS / LLM Judge 评测

演进过程中保留了一些旧接口、旧表和兼容分支。现在前端和数据库都已稳定在
新结构上，可以分阶段清理。

## 2. 清理原则

1. **先删代码兼容层，再做需要备份的数据库迁移。**
2. **涉及删表、删列的操作必须先备份 `data/knowledge.db`。**
3. **历史数据先导出再删除，不直接丢。**
4. **每阶段单独提交，可回滚。**
5. **不删除仍然承担运行时职责的“回退路径”**，例如无 `langgraph` 时的 `_ask_legacy`。

## 3. 当前数据库概况

当前 `init_db()` 初始化后：

- 物理表：31 张
- 业务表：26 张（含 1 张 FTS 虚拟表）
- FTS5 自动影子表：5 张

```text
search_chunks_fts_config
search_chunks_fts_content
search_chunks_fts_data
search_chunks_fts_docsize
search_chunks_fts_idx
```

真实 `data/knowledge.db` 当前有 33 张表，多出两张已归档的旧记忆表：

```text
legacy_assistant_memory
legacy_learning_notes
```

FTS5 影子表由 SQLite 自动维护，**不能手工删除**。

## 4. 表级规划

### 4.1 建议删除的表

| 表 | 原因 | 前置条件 |
|---|---|---|
| `schema_meta` | 只写入版本号，从未读取；`PRAGMA user_version` 已足够 | 无 |
| `legacy_assistant_memory` | 已归档的旧记忆表，代码不再读写 | 先导出 JSON |
| `legacy_learning_notes` | 同上 | 先导出 JSON |

### 4.2 建议删除的列

| 列 | 原因 | 处理 |
|---|---|---|
| `content_tasks.feedback_id` | 任务与反馈已用 `content_task_feedback` 多对多关联，该列未被读取 | 确认 join 表覆盖后删除 |
| `eval_runs.passed` | 永远为 0，没有真正计算 | 要么保存时计算，要么删列并去掉 UI 状态 |
| `feedback.reason` | 旧版自由文本，已被 `reasons_json + comment` 取代 | 先合并到 `comment`，再删除 |
| `feedback.rating` | 新数据固定 1/5，历史 2–4 星仍有参考价值 | 建议保留为历史字段 |

### 4.3 建议保留并补读取入口的表

| 表 | 建议 |
|---|---|
| `feedback_revisions` | 在反馈详情展示“修改历史”，否则只写不读 |
| `feedback_triage_events` | 在反馈详情展示“分诊历史”，否则与 `admin_audit_log` 重叠 |

如果暂时不做 UI，可以在后续版本再决定是否删除。

### 4.4 必须保留的表

| 类别 | 表 |
|---|---|
| 账号/权限/额度 | `users`、`sessions`、`daily_usage`、`permission_catalog`、`permission_requests` |
| 对话/文档 | `conversations`、`answers`、`search_chunks`、`search_chunks_fts` |
| 反馈/轨迹 | `feedback`、`feedback_source_marks`、`answer_traces`、`retrieval_candidates`、`admin_audit_log`、`source_clicks` |
| 任务/正例 | `content_tasks`、`content_task_feedback`、`curated_examples` |
| 实验 | `experiments`、`experiment_variants`、`experiment_assignments` |
| 评测 | `eval_runs`、`eval_results` |

## 5. 代码级规划

### 5.1 可以删除的兼容代码

| 文件/位置 | 内容 | 说明 |
|---|---|---|
| `app/main.py` `FeedbackRequest` | `rating`、`reason` 字段 | 当前前端只传 `sentiment/reasons/comment` |
| `app/feedback.py` | `sentiment_from_rating`、rating 校验、旧前端兼容分支 | 旧 1–5 星兼容 |
| `app/db.py` `save_feedback` | `rating`、`reason` 参数和“兼容旧调用” | 改为只接收 `sentiment/reasons` |
| `app/db.py` `_archive_table` | 旧记忆表迁移逻辑 | 删表后一起删 |
| `app/db.py` `schema_meta` 写入 | 只写不读 | 删除 |
| `app/retention.py` | `legacy_*` 清理项 | 删表后删除 |
| `scripts/archive_memory.py` | 旧记忆导出脚本 | 迁移完成后可删 |
| `tests/test_feedback_taxonomy.py` | 旧 rating + reason 用例 | 改成只测新 API，或删除相关用例 |
| `web/app.js` | 未被 `index.html` 引用的旧前端 | 可删 |
| `evals/requirements-eval.txt` | 未使用的 `llama-index-core` 可选行 | 删除 |

### 5.2 需要修改的代码

| 项 | 现状 | 改法 |
|---|---|---|
| `app/db.py` 末尾 `init_db()` | import 时初始化真实数据库 | 移到 FastAPI lifespan；脚本入口显式调用 |
| `app/eval_store.py` `passed` | 永远为 0 | 保存时计算，或删列并去掉 UI 状态 |
| `app/curated_store.py` | `eval_run_id` 只检查非空 | 校验 run 存在、同一数据集、`passed=1` |
| `app/content_store.py` | `eval_run_id` 可传任意值 | 校验 run 存在 |
| `app/experiments.py` 更新变体 | 运行中可替换变体，用户可能静默掉组 | running 状态禁止改 variants，或保留旧 key |
| `app/experiments.py` 配置合并 | 多个运行中实验可覆盖同一参数 | 启动实验时校验 key 冲突 |
| `app/experiments.py` `MIN_VECTOR_SCORE` | 重排开启时不参与证据判断 | 从允许列表移除，或明确只在 `RERANK_ENABLED=false` 时生效 |
| `app/main.py` CSV 导出 | `username` 未脱敏 | 加入 PII 脱敏字段 |
| `app/main.py` / `app/db.py` | 均超过 1000 行 | 拆成评测、反馈、文档、权限等模块 |

### 5.3 建议补齐的完善项

- Playwright E2E：覆盖登录、提问、👍/👎、提交反馈、修改、管理端打开。
- 反馈提交 loading / 禁用，防重复点击。
- 登录失败限流、CSRF token（对外部署时）。
- FTS 增量更新，避免每次启动全量重建。
- 问题聚类持久化，稳定跟踪内容缺口。
- 审计、评测、内容任务详情的筛选和导出。
- 依赖 lock 文件，避免 CI 解析出未来不兼容版本。
- 日志轮转。

## 6. 分阶段执行计划

### Phase 0：备份

```powershell
python scripts/archive_memory.py
```

使用 SQLite backup API 备份：

```text
data/knowledge.db → data/archive/knowledge_before_v11.db
```

### Phase 1：安全代码清理（不动数据库）

1. 删除 `FeedbackRequest.rating/reason`。
2. `feedback.normalize` 只接受 `sentiment/reasons`。
3. `save_feedback` 去掉旧参数。
4. 更新 `test_feedback_taxonomy`。
5. 删除 `web/app.js`。
6. 删除 `llama-index-core` 可选依赖。

验收：

- 现有前端点赞/点踩正常。
- 104+ 测试通过。
- 旧 `{rating, reason}` 请求返回 422；如仍有外部客户端，暂缓此阶段。

### Phase 2：数据库 v11 迁移

迁移内容：

```sql
UPDATE feedback
SET comment = reason
WHERE comment = '' AND reason <> '';

DROP TABLE IF EXISTS legacy_assistant_memory;
DROP TABLE IF EXISTS legacy_learning_notes;
DROP TABLE IF EXISTS schema_meta;

ALTER TABLE feedback DROP COLUMN reason;
-- 可选：ALTER TABLE content_tasks DROP COLUMN feedback_id;
```

同时：

- 删除 `_archive_table`。
- 删除 `schema_meta` 写入。
- 删除 `retention.py` 中 legacy 项。
- 删除 `scripts/archive_memory.py`。
- 更新 `PRAGMA user_version = 11`。
- 如果 SQLite 版本不支持 `DROP COLUMN`，用重建表方式迁移。

验收：

- 旧库连续 `init_db()` 两次不报错。
- 反馈、轨迹、评测记录数量不变。
- `comment` 已承接旧 `reason`。
- `PRAGMA user_version = 11`。

### Phase 3：处理只写不读和冗余列

二选一：

- **保留历史**：给 `feedback_revisions`、`feedback_triage_events` 加详情读取。
- **彻底精简**：删除两张表，只保留 `admin_audit_log`。

同时：

- 删除 `content_tasks.feedback_id`。
- 决定 `eval_runs.passed` 是计算还是删除。

### Phase 4：结构性问题

1. `init_db()` 移出 import，改 FastAPI lifespan。
2. 实验运行中禁止替换变体。
3. 实验参数冲突校验。
4. 校验 `eval_run_id` 存在且通过。
5. FTS 增量更新。
6. 拆分 `db.py` / `main.py`。

### Phase 5：体验与安全

1. Playwright E2E。
2. 反馈提交 loading。
3. 登录限流 / CSRF。
4. CSV 用户名脱敏。
5. 依赖 lock。

## 7. 风险与回滚

| 操作 | 风险 | 回滚 |
|---|---|---|
| 删除旧 API 字段 | 外部旧客户端 422 | 保留一个版本后再删 |
| 删除 `feedback.reason` | 旧自由文本丢失 | 先合并到 `comment`，并备份 DB |
| 删除 legacy 表 | 归档数据丢失 | 先导出 JSON + 备份 DB |
| 删除 `feedback_revisions` | 失去修改历史 | 先决定是否展示，再删 |
| `init_db` 移到 lifespan | 直接 import 的脚本可能缺表 | 在脚本入口显式初始化 |

## 9. 非目标

- 不改变当前检索、重排、拒答和实验默认行为。
- 不删除 `_ask_legacy`：它是无 `langgraph` 环境的运行时回退，不是旧数据兼容。
- 不删除 `seed_v1`：评测集需要保留历史版本。
- 不手工操作 FTS5 影子表。
